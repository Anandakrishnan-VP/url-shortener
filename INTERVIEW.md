# System Design & Technical Deep-Dive: URL Shortener ("Shortly")

This document prepares you for technical interviews covering the design, implementation, and trade-offs of Shortly.

---

## 1. High-Level Requirements & Calculations

### Functional Requirements
- Shorten any valid HTTP/HTTPS URL with an optional custom alias and expiration timestamp.
- Perform high-speed HTTP 302 redirection to original URLs.
- Track analytics asynchronously (total clicks, clicks per day, device type).
- Web UI to test link creation, redirection, and inspection of analytics.

### Non-Functional Requirements
- High read-to-write ratio (~100:1).
- Sub-10ms redirect latency.
- No single point of collision for short codes.
- High availability and graceful degradation under load.

### Key Calculations: Base62 & Character Length
- **Alphabet size:** 62 characters (`[0-9]`, `[A-Z]`, `[a-z]`).
- A 6-character code yields $62^6 \approx 56.8 \text{ billion}$ distinct URLs.
- A 7-character code yields $62^7 \approx 3.52 \text{ trillion}$ distinct URLs.
- **Offset rationale:** $62^5 = 916,132,832$. Adding $62^5$ to sequence IDs ensures that even the very first ID generated starts with a 6-character code (`100000`), avoiding awkward single-character codes (`0`, `1`, `z`) while preventing enumeration of the system's early IDs.

## 2. Deep Dive: Architectural Decisions & Trade-Offs

### 2.1 Unique Code Generation: Sequence + Base62 vs. MD5/SHA256 Hashing
- **Hashing Approach (MD5/SHA256 + Truncation):**
  - Hash collisions are inevitable (Birthday Paradox). Requires a collision-resolution loop (DB query + re-hash or append counter).
  - High database read contention during writes.
- **Central Sequence + Base62 (Chosen Approach):**
  - Single atomic `nextval('short_url_id_seq')` in PostgreSQL guarantees uniqueness.
  - Zero collisions possible for non-custom links.
  - Bijective mathematical mapping: deterministic, reversible, and $O(1)$ encoding complexity.

### 2.2 In-Memory LRU Cache vs. Redis
- **Why in-memory LRU:**
  - For interview scope and simplicity, zero external dependency is required.
  - Sub-millisecond latency (in-process heap memory lookup is orders of magnitude faster than a network round-trip to Redis).
- **Why `LinkedHashMap` needs synchronization:**
  - `LinkedHashMap` in access-order mode (`true`) rearranges its internal doubly linked list on **every** `get()` call.
  - Concurrent `get()` calls without synchronization cause race conditions, infinite loops, or corrupt node pointers.
  - Wrapped with `Collections.synchronizedMap` to ensure thread-safety across concurrent requests.

### 2.3 Async Click Analytics: Non-Blocking Redirects
- **Problem:** If analytics recording is synchronous, every redirect depends on database write latency. If the DB slows down, redirects slow down.
- **Solution:** `@Async("analyticsExecutor")` with a bounded `ThreadPoolTaskExecutor`:
  - Core pool: 2 threads
  - Max pool: 4 threads
  - Queue capacity: 1000 tasks
  - **Rejection Policy:** Logs a warning and drops the event rather than blocking or throwing an exception to the redirecting user. A dropped analytics counter is preferable to failing a user's redirect.

### 2.4 HTTP 301 vs. HTTP 302 Redirection
- **301 Moved Permanently:** The client browser caches the redirect locally. Subsequent requests go straight to the destination URL without hitting the shortener server.
  - *Downside:* We cannot track click analytics or enforce expiration timestamps after the first redirect!
- **302 Found (Chosen):** The browser does not cache the redirect. Every click hits Shortly, ensuring accurate real-time metrics and dynamic expiration checks.

## 3. Walkthrough of Key Classes

1. **`UrlShortenerApplication`:**
   - Spring Boot entrypoint with `@EnableAsync` to activate Spring's proxy-based async method execution.
2. **`Base62Encoder` (implements `CodeEncoder`):**
   - Converts `long` sequence IDs into base62 representations and decodes base62 strings back into `long`.
3. **`ShortUrl` & `ClickEvent`:**
   - JPA entities matching the Flyway schema. `ShortUrl` uses a sequence-assigned `@Id` (not generated by Hibernate) to synchronize with the Base62 encoder.
4. **`LinkCache` & `LruCache`:**
   - Custom access-order map overriding `removeEldestEntry(size > capacity)` wrapped in thread-safe synchronization.
5. **`UrlServiceImpl`:**
   - Enforces URL validation, reserves critical system routes, manages sequence ID assignment, coordinates LRU caching, and calculates analytics queries.
6. **`AnalyticsService`:**
   - Inspects `User-Agent` strings with fast substring matching to identify Mobile, Tablet, Desktop, or Bot clients, recording events asynchronously.
7. **`GlobalExceptionHandler`:**
   - Central `@RestControllerAdvice` converting application domain exceptions into clear HTTP 400, 404, 409, and 410 JSON responses.

## 4. Frequently Asked Interview Questions

**Q: What happens if two users request the same custom alias simultaneously?**
- *Answer:* The database table has a `UNIQUE` constraint on `short_code`. Even if both requests pass the initial `existsByShortCode` check simultaneously, one will succeed and the other will trigger a database constraint violation handled as HTTP 409 Conflict.

**Q: How do you handle expired links in the cache?**
- *Answer:* When `resolve(code)` fetches a link from the LRU cache, it checks `cachedLink.isExpired()`. If expired, it immediately evicts the link from the cache and throws `LinkExpiredException` (mapped to HTTP 410 Gone).

**Q: Why use `CAST(clicked_at AT TIME ZONE 'UTC' AS date)` in the repository query?**
- *Answer:* Timestamps are stored in UTC. Casting to date within UTC ensures consistent daily aggregation regardless of the database server's local system timezone.
